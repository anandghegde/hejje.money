# Phase 8 — Daily market context (ratings, market condition, bases, historical analogs)

Goal of the phase: give Hejje a nightly, deterministic research layer over a wide daily universe, modelled on three
products the user pointed at on 2026-09-20:

- **Konseki** (konseki.io): match the current setup against history across the whole universe, measure what followed
  (win rate, median, 25–75 band, MAE/MFE), rank by evidence, list every match, tag thin evidence, immutable daily
  snapshots.
- **MarketSmith India**: RS and accumulation/distribution ratings, off-high/off-low, volume surge, industry group rank,
  the market condition call (Confirmed Uptrend / Under Pressure / Rally Attempt / Downtrend), base and pivot
  recognition, near-pivot and stocks-on-the-move lists, a screener with saved screens.
- **TraderSmith**: one prioritised list (in buy zone → triggered → waiting), a trade plan per stock (buy zone, profit
  goal, stop), annotated charts, alerts when a stock enters a buy zone, a past-setups ledger.

Hejje stays an intraday system. This phase produces **context and evidence**: it selects and gates what the intraday
strategies trade, and it is shown on its own screens. It places no orders and holds nothing overnight.

Decisions taken with the user (2026-09-20):

| Question | Decision |
|---|---|
| Universe | NIFTY 500, **D1 only**, ~10 years where Kite has it. Intraday M1/M5 stays NIFTY 50 + indices |
| Fundamentals (EPS, SMR, Composite) | Skipped: Kite has no fundamentals. The composite here is a **technical** composite |
| Swing execution (CNC, overnight) | Not decided, so not planned. See "Out of scope for the phase" for what it would touch |
| Analog horizon | Both: daily analogs (Konseki's shape) on NIFTY 500, and session analogs (intraday) on the M5 universe |
| Role of the new numbers | Evidence first. They change a score, a decision or a universe only after M8.8 passes |

Binding rules for this phase (on top of plan/README §4):

- **No look-ahead, by construction.** Every rating, condition, base and analog for session date `D` is a function of
  candles up to and including `D`'s close, walked forward like `regime/internal/DailyWalker`. A match's lookback window
  and forward window both end before the benchmark date. SIM reads are capped at the simulation clock (M7.2 guard).
- **Immutable snapshots.** A row for `(date, instrument, engine-version)` is written once. A rule or threshold change
  bumps the engine version and writes new rows; it never rewrites old ones (same contract as
  `hejje.regime.classifier-version`).
- **Sample size before percentage.** Every aggregate carries its count; an API response, a screen or a templated
  sentence never shows a rate without it. Below `min-evidence` the direction tag is `INSUFFICIENT`.
- **Templated prose only** (README rule 11). The plain-language read is built from the evidence fields with hedged
  wording ("historically leaned", "in similar past sessions"); no LLM in this phase.
- **Off the trading core.** The modules are feature-flagged (`hejje.ratings.enabled`, `hejje.analogs.enabled`, default
  off); execution, signals and risk run unchanged with them off or failing.
- **Floats are allowed here.** Returns, distances and ratings are statistics, not money; `double` is fine. Pivot, buy
  zone and stop prices are `BigDecimal` rounded to tick size.

New modules: `money.hejje.ratings` (daily ratings, groups, bases, lists, screens, watchlist) and `money.hejje.analogs`
(daily and session analog engines). The market condition is a new dimension of the existing `regime` module.
Migrations start at V38.

Order: M8.1 → M8.2 → M8.3 → M8.4 → M8.5 → M8.6 → M8.7 → M8.8 → M8.9. M8.3 needs only M8.1. M8.7 can start against
M8.2–M8.4 while the analog milestones are in progress. M8.9 builds only what passed M8.8.

## M8.1 NIFTY 500 daily universe and data  (size: M, part ops on the VM)

**Goal.** Ten years of clean, adjusted D1 candles for the NIFTY 500, kept current every evening.

**Tasks.**
1. `config/universe/nifty500.yaml` in the `nifty50.yaml` shape plus an `industry` per symbol, generated by
   `research/tools/gen_universe.py` from NSE's `ind_nifty500list.csv` (columns Company Name, Industry, Symbol, Series,
   ISIN). The file is committed; the script is re-run at the semi-annual index reviews. Symbols that do not resolve in
   the instrument master are reported, not dropped silently.
2. Universe backfill: `POST /api/v1/market/history/backfill-universe {universe, timeframe, from, to}` (scope `admin`)
   fans out into the existing per-instrument backfill jobs under the `historical-per-second` throttle and returns one
   parent job id; `GET /market/history/jobs/{id}` reports children done/failed. D1 allows long ranges per request, so
   500 symbols × 10 years is on the order of 1,000 requests (~6 minutes at 3/s). Verify the D1 range limit against
   the current Kite docs first.
3. Evening D1 refresh: a `@Scheduled` job at `hejje.ratings.daily-refresh-time` (18:30 IST) backfills the last 5
   sessions of D1 for the universe (idempotent upsert), then publishes `DailyCandlesRefreshed(date)`; M8.2–M8.5 chain
   off that event. Registered in the `SimJobs` registry as `SKIP` (SIM reads stored history).
4. Adjustment check: Kite daily history is adjusted for splits and bonuses, not dividends. Extend the integrity report
   with a `suspectGaps` list (|close-to-open| ≥ 35 % with no matching move in the index) so an unadjusted split is
   seen before it poisons RS and analogs. A re-backfill of the affected symbol is the fix; no adjustment logic here.
5. `docs/data.md`: the new series row, the procedure, and the known limitation: **survivorship bias** (today's
   constituents only; delisted and demoted stocks are missing), which flatters every historical statistic built on it.
   M8.8 measures on recent data for that reason.

**Acceptance.** Coverage shows ≥ 480 of 500 symbols with D1 from 2016 or their listing date; the integrity report lists
no unexplained suspect gaps; the evening job brings a stale universe current in one run.

**Verification.** `./gradlew test --tests '*UniverseBackfill*' --tests '*SuspectGap*'` (WireMock Kite, fake clock); on
the VM: run the backfill, paste the coverage summary and the suspect-gap list into PROGRESS.

**Out of scope.** Intraday data for the 500; BSE; point-in-time index membership.

## M8.2 Daily ratings and industry groups  (size: M)

**Goal.** MarketSmith's price/volume ratings block for every stock in the universe, per session, reproducible.

**Tasks.**
1. `ratings` module, table `daily_rating(session_date, instrument_id, engine_version, rs_raw, rs_rating, ad_raw,
   ad_grade, off_high_pct, off_low_pct, vol_vs_avg50_pct, up_down_vol_ratio, avg_turnover_cr, group_id, group_rank,
   tech_composite, evidence jsonb)`, primary key on the first three. ~1.25 M rows for ten years; plain Postgres.
2. Formulas (documented in `docs/ratings.md`, thresholds in `config/ratings.yaml`):
   - **RS rating**: `rs_raw = 0.4·ret(63) + 0.2·ret(126) + 0.2·ret(189) + 0.2·ret(252)` on sessions; `rs_rating` is the
     1–99 percentile within the universe that day. Needs 252 sessions; younger listings use the quarters they have,
     with `evidence.partial=true`, and none below 63.
   - **A/D grade**: over 65 sessions, `Σ clv·volume / Σ volume` with `clv = ((close−low) − (high−close)) / (high−low)`
     (0 on a zero range); universe percentile mapped to `A+ … E` (13 grades, equal-width bands).
   - **Off high / off low**: close vs the 252-session high and low. **Volume vs average**: today's volume vs the
     50-session mean. **Up/down volume ratio**: 50 sessions.
   - **Industry groups**: one group per `industry` in the universe file; `group_strength` = median `rs_raw` of members
     with ≥ 3 members; `group_rank` 1..N. Table `industry_group_rank(session_date, group_id, rank, strength, members)`.
   - **Technical composite** 1–99: percentile of `0.5·rs + 0.2·ad + 0.15·group + 0.15·offHigh` component percentiles.
     Named "technical" everywhere so it is never mistaken for O'Neil's Composite (which needs EPS and SMR).
3. `RatingsEngine` walks sessions forward (`DailyWalker` style). `POST /api/v1/ratings/compute {from, to}` (admin)
   computes history; the `DailyCandlesRefreshed` listener computes the day. Re-running a date is a no-op.
4. API (scope `market:read`): `GET /ratings/{symbol}?date=`, `GET /ratings?date=&sort=&minRs=&group=&limit=`,
   `GET /ratings/groups?date=`, `GET /ratings/{symbol}/history?from=&to=`. `date` defaults to the latest computed
   session and is capped at the simulation clock in SIM.

**Acceptance.** Same candles and engine version give byte-identical rows (hash in the job result, as the regime label
job does); ratings for date `D` do not change when candles after `D` are added.

**Verification.** `./gradlew test --tests '*RatingsEngine*'`: golden fixture of 12 synthetic symbols × 300 sessions
with hand-checked RS ranks and A/D grades; a no-look-ahead test (append future candles, recompute, compare);
`ApplicationModules.verify()`.

**Out of scope.** EPS/SMR/Composite, peer comparison on fundamentals, ASM/GSM surveillance flags (follow-up: NSE
publishes the lists as CSV).

## M8.3 Market condition  (size: M)

**Goal.** The daily market call as a seventh regime dimension: `CONFIRMED_UPTREND | UPTREND_UNDER_PRESSURE |
RALLY_ATTEMPT | DOWNTREND | UNKNOWN`.

**Tasks.**
1. Volume proxy: `INDEX:NIFTY 50` carries no volume, so index volume for a session is the summed D1 turnover
   (`close × volume`) of the `nifty50.yaml` constituents. Documented in `docs/regime.md`; `UNKNOWN` when fewer than 45
   constituents have a candle.
2. Rules in `RegimeRules`, thresholds in `config/regime.yaml`:
   - **Distribution day**: index close ≤ −0.2 % on higher proxy volume than the previous session. A day drops out of
     the count after 25 sessions or once the index closes 5 % above that day's close.
   - **Rally attempt**: in `DOWNTREND`, the first up close after a new low starts day 1; an undercut of that low
     resets the count.
   - **Follow-through day**: on day 4 or later of a rally attempt, index up ≥ 1.25 % on higher volume →
     `CONFIRMED_UPTREND`.
   - `CONFIRMED_UPTREND` → `UPTREND_UNDER_PRESSURE` at ≥ 4 distribution days in 25; → `DOWNTREND` at ≥ 6, or a close
     below the 50-DMA with ≥ 5. `UPTREND_UNDER_PRESSURE` → `CONFIRMED_UPTREND` when the count falls to ≤ 3.
3. `MarketCondition` enum and field on `RegimeSnapshot` with the evidence list (distribution-day dates, rally day
   number, follow-through date). State machine carried in `DailyState`. Bump `hejje.regime.classifier-version`;
   relabelling history is the existing job.
4. Surfaces that already carry regime get it for free where they iterate dimensions: regime API and history, Pulse
   label table (one new row), `get_market_regime` tool. Add the row where a surface lists dimensions by hand.
5. Notification event `MARKET_CONDITION_CHANGED` (INFO; WARNING into `DOWNTREND`).

**Acceptance.** Relabelling 2016→today gives a plausible, stable sequence (paste the transitions of the last three
years into PROGRESS and eyeball them against known corrections); label hash is reproducible.

**Verification.** `./gradlew test --tests '*MarketCondition*'`: scripted index series for each transition, the
distribution-day expiry rules, the undercut reset, `UNKNOWN` on missing constituents.

**Out of scope.** Gating entries on the condition (M8.9, after validation); a separate call for NIFTY BANK.

## M8.4 Bases, pivots and the trade plan  (size: L; split detection and lifecycle if needed)

**Goal.** Chart pattern recognition on D1 with TraderSmith's trade-setup block: buy zone, stop, profit goal, status.

**Tasks.**
1. Detectors in `ratings/internal/bases`, deterministic, thresholds in `config/ratings.yaml`, each requiring a prior
   uptrend (≥ 25 % advance into the base):
   - **Flat base**: ≥ 25 sessions, depth ≤ 15 %; pivot = base high.
   - **Cup with handle**: cup 35–325 sessions, depth 12–35 %, right side recovers ≥ 90 % of the left high; handle ≥ 5
     sessions in the upper half, depth ≤ 12 %; pivot = handle high. Cup without handle: pivot = left high.
   - **Double bottom**: two lows within 3 %, second undercuts the first or not by config, ≥ 35 sessions; pivot = the
     middle peak.
   - **Moving-average reversal** (TraderSmith's "trend reversal day"): in an uptrend (close > 50-DMA rising), a session
     that trades down to the 20- or 50-DMA and closes in the upper 40 % of its range above it; pivot = that session's
     high, undercut level = its low.
2. Trade plan per base: `buy_zone = [pivot, pivot × 1.05]`, `stop = pivot × 0.93` (reversal setups: the undercut low),
   `profit_goal = pivot × 1.20` for bases and `× 1.08` for reversals; all tick-rounded `BigDecimal`. Informational
   only: nothing in Hejje trades it in this phase.
3. Lifecycle, advanced once per session by the daily job: `FORMING → NEAR_PIVOT (within 5 % below) → IN_BUY_ZONE
   (close in zone; `volume_confirmed` when breakout volume ≥ 1.4 × avg50) → EXTENDED (> 5 % above) → HIT_GOAL | STOPPED
   | FAILED (closes back below pivot by > 7 %) | EXPIRED`. Table `base(id, instrument_id, type, start_date, end_date,
   depth_pct, pivot, buy_low, buy_high, stop, goal, status, status_date, engine_version, evidence)` plus
   `base_status_history`. Closed bases are the **past setups** ledger with realised outcome in % and in R.
4. Lists, as queries over ratings + bases: **In buy zone**, **Near pivot**, **Leaders** (tech composite ≥ 85, RS ≥ 80,
   turnover ≥ `min-turnover-cr`), **Stocks on the move** (|chg| ≥ 2 % and volume ≥ 1.5 × avg50, up and down), **Top
   groups**. The combined TraderSmith ordering is one endpoint: in buy zone, then triggered and extended, then near
   pivot, each by tech composite.
5. API: `GET /ratings/bases?status=&type=&date=`, `GET /ratings/{symbol}/bases`, `GET /ratings/lists/{name}?date=`,
   `GET /ratings/setups/past?from=&to=`. Notification events `ENTERED_BUY_ZONE`, `NEAR_PIVOT`, `SETUP_STOPPED`,
   `SETUP_HIT_GOAL`, fired for watchlist symbols and Leaders only (M8.7 adds the watchlist; until then Leaders).

**Acceptance.** Each detector finds its synthetic fixture and rejects the near-miss variants (too deep, too short, no
prior uptrend); a base's fields never change after detection except status; history backfill 2016→today completes and
the past-setups ledger reports hit-goal / stopped / failed counts per type (paste into PROGRESS: this is the first
honest read on whether the patterns are worth anything on this universe).

**Verification.** `./gradlew test --tests '*BaseDetector*' --tests '*BaseLifecycle*'` with golden series under
`server/src/test/resources/bases/`; no-look-ahead test as in M8.2.

**Out of scope.** Weekly charts, ascending bases, high tight flags, base counting (stage 1/2/3), analyst notes.

## M8.5 Daily analog engine  (size: L)

**Goal.** Konseki's engine on the NIFTY 500 D1 store: for each symbol and lookback, the historical windows anywhere in
the universe that looked like now, and what followed them.

**Tasks.**
1. `analogs` module. Lookbacks `5, 10, 15, 20, 25, 30, 40, 50` sessions; forward windows `3, 5, 10, 15` sessions
   (config). A window's features: z-normalised log-close path, realised volatility, regression slope, position in its
   own high–low range, volume z-score vs the prior 50 sessions, max drawdown inside the window.
2. Seven distance components per candidate, as Konseki names them: `path_correlation`, `shape_distance` (Euclidean on
   the normalised path), `volatility_distance`, `trend_distance`, `range_position_distance`, `volume_distance`,
   `risk_distance`. `similarity_score` = weighted sum of the components scaled by their universe-wide standard
   deviation (weights in `config/analogs.yaml`, shape-heavy by default); lower is closer.
3. Search: a candidate is any (symbol, end date) whose lookback **and** longest forward window end before the benchmark
   date. Scalar prefilter (volatility, slope, range position within configured bands) before the path distance, so the
   engine holds only per-symbol close/volume arrays in memory (~10 MB), not a window matrix. Keep the best
   `max-matches` (50) under `max-distance`, after de-overlapping: one match per symbol per `2 × lookback` span, and the
   benchmark symbol's own recent windows are excluded for `lookback + max forward` sessions.
4. Match quality 1–5 per match from six component scores (shape, trend, volatility, range position, volume, risk), each
   a documented piecewise mapping of its raw distance (`scoring/internal/PiecewiseLinear` style, copied not shared
   across modules), plus the aggregate `quality_tag` `STRONG | MODERATE | WEAK` from the median.
5. Outcomes per forward window over the match set: count, win rate, mean, median, p25/p75, the average path and 25–75
   band day by day, MAE and MFE (median and p75), best and worst. Tags with documented thresholds:
   `direction` (`BULLISH_STRONG … BEARISH_STRONG | MIXED | INSUFFICIENT`, from win rate and median together),
   `consistency` (IQR), `reliability` (count, distinct symbols, distinct years), `risk` (MAE), `outlier` (mean moves
   by more than a configured share when the two most extreme matches are dropped).
6. Seasonality as Konseki does it: the same match set split into same-calendar-month and other-months, outcomes per
   group with counts. `benchmark.context` reports the symbol's scalar features across all eight lookbacks.
7. Storage: `analog_summary(session_date, instrument_id, kind, lookback, engine_version, summary jsonb)` kept forever
   (small); `analog_match(...)` rows kept for `hejje.analogs.match-retention-days` (30) and for every date M8.8 asks
   for. `kind = DAILY` here, `SESSION` in M8.6.
8. Templated read (`AnalogNarrative`): distribution, risk, reliability, match quality, takeaway; five sentences built
   from the fields, including the "be careful" variants for `INSUFFICIENT`, `WEAK`, high `risk` and `outlier`.
9. Nightly run after ratings on `DailyCandlesRefreshed`, parallel across symbols on virtual threads, bounded by
   `hejje.analogs.parallelism`. `POST /api/v1/analogs/compute {dates, symbols?, lookbacks?}` (admin) for history.
   API (scope `market:read`): `GET /analogs/{symbol}?lookback=15&date=`, `GET /analogs/{symbol}/matches?lookback=&date=`
   (unordered, client sorts, no `rank` field), `GET /analogs/rank?lookback=&forward=&sort=winRate|median|count|
   reliability&minCount=&date=` for the ranked universe.

**Acceptance.** Deterministic (summary hash per date); a planted fixture (the benchmark path copied into another
symbol's history with a known forward move) is the top match with the expected outcome; no match's windows reach the
benchmark date; the nightly run for 500 symbols × 8 lookbacks finishes within `hejje.analogs.nightly-budget` (30 min)
on the VM, measured and pasted into PROGRESS. If it does not, cut lookbacks in config before optimising.

**Verification.** `./gradlew test --tests '*AnalogEngine*' --tests '*AnalogOutcome*' --tests '*AnalogNarrative*'`;
no-look-ahead test; an overlap test (two windows of one symbol ten days apart yield one match).

**Out of scope.** Indices, futures and cross-exchange universes; DTW or learned embeddings; an approximate-nearest-
neighbour index (only if the budget fails after the prefilter).

## M8.6 Session analogs (intraday)  (size: M)

**Goal.** The same question at Hejje's own horizon: sessions that looked like today's so far, and how they closed.

**Tasks.**
1. Universe: the instruments with M5 history (NIFTY 50 constituents, the two indices, continuous futures). Candidates:
   every past session of every instrument in that universe (~50 k today).
2. Checkpoints `09:45, 10:15, 11:15, 13:00` IST (config). Features at a checkpoint: the M5 close path from the open,
   expressed in previous-close returns (so the gap is part of the shape); session range so far vs D1 ATR(14); position
   in the opening range; cumulative volume vs the 20-session same-time average; drawdown so far; prior-session return
   and D1 range position. Distances and quality reuse M8.5's code with a session weight set.
3. Forward outcome: checkpoint → 15:10 (the force-exit time), in % and in D1-ATR multiples: return, MAE, MFE, time of
   the session high and low, and whether the checkpoint-time high/low held. Same tags, seasonality omitted,
   weekday/expiry-day split instead (same-weekday vs other, expiry-day vs not), with counts.
4. Computed live at each checkpoint by a `@Scheduled` job for the deployed strategies' instruments plus the watchlist
   (brute force is milliseconds at this size); stored as `kind = SESSION` summaries and matches. Registered in
   `SimJobs` as `RUN`; candidates are limited to sessions before the simulation date.
5. API: `GET /analogs/session/{symbol}?checkpoint=&date=`; pushed on `/ws/events` as `SessionAnalogsUpdated`.

**Acceptance.** A SIM replay of a fixture day produces the same summaries as the live path on that day's recorded
data; no candidate is from the benchmark date or later.

**Verification.** `./gradlew test --tests '*SessionAnalog*'`; `SessionAnalogSimIT` (single shared context, per the
IT-suite rules).

**Out of scope.** Tick-level features, options, analogs as an entry trigger.

6. Docs: `docs/ratings.md`, `docs/analogs.md` (methodology: every formula, threshold, tag rule and known limitation,

Playwright smoke for the two pages; `go test ./...` with the new golden renders.

## M8.8 Validation: do these numbers predict anything?  (size: M, mostly a run and a report)

**Goal.** A pre-registered test, in the style of M6.5, of each claim before it is allowed to change a decision.

**Tasks.**
1. `docs/strategies/context-validation.md` written and committed **before** any run: hypotheses, ranges, metrics, pass
   marks. Evaluation range: the last 24 months; nothing in it was used to pick a threshold (thresholds come from the
   O'Neil literature or were fixed in M8.2–M8.6). Survivorship bias is stated as a caveat on every daily-universe
   result.
2. Hypotheses (each with its pass mark in the doc):
   - **H1 daily analogs**: forward 5- and 10-session returns of `BULLISH_*` vs `BEARISH_*` vs the unconditional
     universe base rate, by reliability bucket; computed on every 5th session, lookbacks 15 and 30, to bound compute.
   - **H2 session analogs**: checkpoint→15:10 return by direction tag vs base rate, per checkpoint.
   - **H3 stock selection**: the Phase 6 strategies that passed the bake-off, re-run with the universe restricted per
     session to the top-N NIFTY 50 stocks by RS (longs) / bottom-N (shorts), vs unrestricted, same ranges and costs.
   - **H4 market condition gate**: the same strategies with longs allowed only in `CONFIRMED_UPTREND` /
     `UPTREND_UNDER_PRESSURE`, vs ungated.
   - **H5 bases**: from the M8.4 ledger, expectancy in R per base type with and without `volume_confirmed`, and by
     market condition at the trigger. Informational (nothing in Hejje trades it); it decides whether a swing phase is
     worth planning.
   H3 and H4 need a per-session filter in the backtester; implement it as a research-only backtest request option
   (`sessionFilter`: allowed instruments and allowed sides per date, supplied by the script from the snapshots), not as
   a DSL feature yet.
3. `research/tools/context_validation.py` (standard library, like `bakeoff.py`): `plan`, `run`, `report`; writes the
   results table and the verdict per hypothesis into the doc.

**Acceptance.** The report exists with every hypothesis marked PASS / FAIL / INCONCLUSIVE against its pre-registered
mark, including the ones that failed. A FAIL is a valid outcome of this milestone.

**Verification.** The script's `plan` output and the final table pasted into PROGRESS; the doc's git history shows the
protocol commit before the results commit.

**Out of scope.** Tuning thresholds on the evaluation range; a second attempt at a failed hypothesis without a new
pre-registration on new data.

## M8.9 Integration of what passed  (size: M; every task is conditional on its hypothesis)

**Goal.** Let validated context influence ranking and selection, bounded and explained, without touching execution.

**Tasks.**

## Out of scope for the phase

- **Swing execution.** Holding the M8.4 setups for days means CNC product type, no force-exit for those positions,
  overnight and gap risk limits in the risk engine, delivery costs in `CostModel`, a D1 backtest mode, multi-day SIM
  sessions and a second P&L horizon in analytics. That is a phase of its own (candidate Phase 9), PAPER-only first,
  and worth planning only if H5 shows positive expectancy.
- **Fundamentals**: EPS, SMR and the true Composite rating, ten-year financials, peer comparison. Needs a licensed
  data source; a manual CSV import is the cheapest later route.
- **AI verdict** (bull/bear case, news catalyst, red flags, conviction). The news and LLM modules could produce a
  per-stock brief as context later; the user chose plain technical analysis for decisions (2026-09-18).
- Analyst-curated picks, model portfolios, webinars, pricing tiers, a public API.
